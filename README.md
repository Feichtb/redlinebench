# RedlineBench

An open benchmark measuring how well AI models review architectural construction documents — finding errors, inconsistencies, omissions, and coordination failures that would cause real problems during construction.

**[View the results](https://redlinebench.benfeicht.com)** | **[Methodology](#methodology)**

## What This Is

Architects spend significant time reviewing drawing sets for coordination errors before issuing them for construction. RedlineBench tests whether AI can do this work reliably by giving models a real residential drawing set (with known issues seeded in) and scoring their findings against a 58-issue answer key.

This is a **QAQC benchmark**, not a design benchmark. It measures a model's ability to catch mistakes in completed documents — the same work an architect does during a quality review before issuing for bid or construction.

## Methodology

1. **Test dataset**: A real residential project drawing set and specification booklet, both with known issues intentionally seeded across 7 categories (schedule-to-drawing conflicts, dimensional errors, spec-to-drawing conflicts, building envelope issues, code/life safety, constructability, and completeness/clarity).

2. **Prompt**: A model-agnostic review prompt ([`review.txt`](results/dataset/prompts/review.txt)) that instructs the model to perform a thorough QAQC review.

3. **Execution**: Each model receives the same prompt and both PDFs via its native API. The [runner](redlinebench/runner.py) saves the full response, token counts, latency, and cost.

4. **Triage**: Each model's response is triaged against the answer key using an [AI-assisted triage prompt](results/dataset/prompts/scoring/prompt1_triage.txt). The triage maps each finding to the answer key and flags unmatched findings for human review. When a model identifies something genuinely new, the finding is reviewed and categorized as a new scoreable issue, a neutral finding (debatable/out-of-scope), or an incorrect finding (model misread the documents). The answer key is locked per release, and any changes create a new version that requires full rescoring. 

5. **Scoring**: Each response is scored against the [answer key](results/dataset/benchmark-answer-key.md) at the issue level:
   - **1 point** — found and correctly described
   - **0.5 points** — found but vague or incomplete
   - **0 points** — missed
   - **-1 point** — per incorrect finding (model misread the documents)

   Scoring is human-verified. The triage prompt assists with matching, but all final scores and answer key decisions are made by a licensed architect, who spot-checks automated scoring passes before publication rather than logging a formal approval per run.

6. **Aggregation**: models may be run and scored more than once. Every scored run is a permanent record — nothing is deleted or overwritten, including runs that score differently from other runs of the same model. [`redlinebench/build_data.py`](redlinebench/build_data.py) reads every `redlinebench/outputs/*/scores.json` and writes `results/dataset/data.json`, which the results page fetches directly. For a model with more than one run, the site shows the mean net score with its min–max range, and the issue-level heatmap shows what fraction of runs caught each issue (e.g. `4/5`) instead of a single pass/fail mark.

## How Runs and Scoring Work

- **Add a new run**: `python runner.py --models <model-key>` (add `--runs N` for several in one batch) from `redlinebench/`. See "Running the Benchmark Yourself" below for the full setup and CLI reference.
- **Score it**: follow [`results/dataset/prompts/scoring/`](results/dataset/prompts/scoring/) to produce a `scores.json` in that run's output folder. This is the only place scoring data lives — it's never copied by hand into the results page.
- **Regenerate published data**: `python build_data.py` from `redlinebench/`. This reads every `scores.json`, aggregates by model (mean/min/max net score, per-issue reliability), and writes `results/dataset/data.json` (fetched by the site) and `results/dataset/data/*.csv`/`.jsonl` (for the Hugging Face dataset viewer) from the same source — there's one place scoring data lives and one script that reshapes it for each consumer.
- **Publish the Hugging Face dataset**: `results/dataset/` is a normal folder in this repo — the *same* files the site and the runner use, not a separately maintained copy. After regenerating, mirror it to a Hugging Face Hub dataset repo yourself (e.g. `huggingface-cli upload <your-hf-repo> results/dataset .` or `git subtree push --prefix=results/dataset`) whenever you want the published dataset to catch up — this isn't automated.

### Versioning

This is **v1** of RedlineBench. If the answer key or drawing set changes in a way that would invalidate direct comparison to these numbers, that becomes a new version — never a silent edit to v1's published results. Any future private/internal benchmark version will be calibrated against this public v1 via bridge runs (re-running a few models on both versions and confirming relative rankings hold) before its results are presented as comparable to v1's.

## Limitations

- **Single evaluator**: The answer key reflects the judgment of one architect reviewing one drawing set. Other architects may reasonably disagree on whether specific findings are scoreable, neutral, or incorrect. The answer key and all scoring data are published in full so others can evaluate for themselves.
- **Single drawing set**: Results reflect model performance on one residential project. Performance on other project types (commercial, institutional, multi-family) or other document formats may differ.
- **Answer key may grow**: The 58-issue answer key represents known issues at the time of this release. Models occasionally surface genuine findings not yet in the answer key. These are reviewed and, if valid, will be incorporated into a future answer key version with full rescoring of all models.

## Running the Benchmark Yourself

### Setup

```bash
cd redlinebench
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# Edit .env — add API keys and PDF paths (see .env.example)
```

### Running

```bash
# All models, 1 run each (default)
python runner.py

# Specific models only
python runner.py --models claude-opus-4-6 gpt-4o

# Multiple runs per model (max 5)
python runner.py --models claude-sonnet-4-6 --runs 3

# Different prompt file
python runner.py --prompt my_custom_prompt.txt

# After scoring, regenerate the published data
python build_data.py
```

### Output structure

Each batch creates a timestamped folder:

```
redlinebench/outputs/YYYY-MM-DD_HH-MM/
├── claude-opus-4-6_run01.txt        ← extracted text response
├── claude-opus-4-6_run01_raw.json   ← full raw API response object
├── manifest.json                    ← token counts, latency, cost, temperature, prompt_version, errors
└── scores.json                      ← added once scored — the permanent per-run scoring record
```

The `manifest.json` records: prompt filename, prompt version, models run, per-model token counts, temperature, cost, and any errors encountered. Models that fail do not abort the run — their errors are logged in the manifest and the remaining models continue.

`temperature` is the value actually sent to the provider for that call (`null` if the provider doesn't accept the parameter, e.g. some reasoning models). `prompt_version` is auto-derived from the prompt filename (`review.txt` → `v1`, `review_v2.txt` → `v2`) as a convenience default — the scorer's `prompt_version` field in `scores.json` remains the authoritative record, since in practice `review.txt` has sometimes been revised in place without a rename.

**Never edit the prompt file after it has been used for a scored run.** If you need to change the prompt, create a new file (e.g. `review_v2.txt`) and pass it with `--prompt`. This ensures every output can be traced back to an exact prompt.

**Do not delete the `redlinebench/outputs/` folder between runs.** Each run folder is a permanent record of the experiment. Multiple runs of the same model are expected and encouraged — every run counts toward that model's aggregate stats in `build_data.py`; none is treated as a "canonical" replacement for another.

## Design Decisions

- **Answer key locked per release** — all scores in a release are against the same answer key. If the answer key changes (new issues added, categories revised), it becomes a new version and all models are rescored from their original outputs.
- **No design advice in scope** — this is QAQC only (post-completion drawing review), not design feedback.
- **No cap on items flagged** — models decide when to stop; this is intentional.
- **Neutral findings have no score impact** — debatable items are tracked but don't affect the score either way.
- **Raw model outputs are included** — every response is in [`redlinebench/outputs/`](redlinebench/outputs/) for full transparency.
- **Multiple runs are permanent, not replaceable** — a model can be run and scored more than once; every run counts toward that model's aggregate stats, and none is treated as a "canonical" replacement for another.
- **One generated source of truth, one copy of every file** — `results/dataset/data.json` and the Hugging Face export are both produced from `redlinebench/outputs/*/scores.json` by the same script (`build_data.py`); neither is hand-edited. The test PDFs, prompts, and answer key each exist in exactly one place (`results/dataset/`) — there's no separate copy for Hugging Face to keep in sync.

## Audience

This benchmark is built for **architects and architecture firm owners** evaluating whether and how to use AI in their practice. Results are designed to be clear and practical, not statistically complex.
